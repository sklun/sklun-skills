# 原生任务清单与条目导入

## 选择任务载体

- 先根据上下文确定用户要在云文档内、原生任务中心还是多维表格中操作。用户提供文档／知识库链接并要求在文档里完成时，不能仅创建独立任务清单后返回 AppLink；在创建远程对象前先核实文档内目标组件的 CLI 支持情况。
- 用户需要勾选完成、区分未完成和已完成、提醒、负责人或子任务时，优先考虑飞书原生任务清单。用户已指定多维表格时按其选择执行；已有多维表格只有在用户要求迁移后才创建原生任务。
- 多维表格中的「状态」单选值与原生任务的完成状态不同。前者通过筛选、分组展示；后者有原生完成动作和完成状态筛选。不要把在 Base 中新增「任务清单」数据表当作创建原生任务清单。
- 原生清单使用 Task GUID 和 AppLink；知识库链接先解析底层资源。不要把 Task GUID 当作 Wiki node token，或承诺将原生清单直接移动成知识库节点。

## 文档内任务的能力边界

- 文档正文操作走当前 `lark-doc` 的创建或更新流程。其 XML 扩展标签支持 `<task task-id="TASK_GUID"/>` 挂载单个已有原生任务；普通 `<checkbox>` 是复选项，不能当成原生任务清单。
- 逐条挂载任务与嵌入整份可筛选、可切换视图的任务清单组件是不同能力。截至本次核验，当前 CLI 文档指南明确支持单任务挂载，未提供整份清单组件的写入命令或标签。以后以当前指南、help 和 schema 为准；不能因网页支持粘贴清单链接就声称 CLI 也支持。
- 用户要求的整份清单组件没有 CLI 支持时，反馈此限制。可以说明逐条挂载方案，但不自行创建替代文档，不以普通链接或逐条任务块冒充完整组件，不回退浏览器操作。
- 已有清单和任务可以在明确选择受支持方案后复用，避免重新导入；仅当文档写入并回读验证后，才交付为文档内可用。

## 读取与映射

先读当前 CLI 的 `lark-task`，按其指南发现命令并核对帮助。来源为多维表格时同时读 `lark-base`，解析 Base 与 Table，读取字段 schema 和全部所需记录。优先将记录写入临时 NDJSON，检查 `has_more` 后再统计。

以本次读取结果为准，不沿用先前对话中的行数。区分有任务内容的条目与只有分类等信息的占位行；无任务内容的占位行不创建任务，报告跳过数量。没有标题但有实质描述的记录，依据内容给出忠实标题，无法判断时再询问。

| 来源信息 | 原生任务目标 |
|---|---|
| 任务名称、任务描述 | `summary`、`description` |
| 负责人 | 任务 assignee；迁移时保留源负责人，缺失时留空，不因当前用户执行导入就统一改为当前用户 |
| 起始日期、截止日期 | 原生 `start`、`due`；只有日期时使用全天任务，按 `Asia/Shanghai` 核对日历日期 |
| 需求／问题、等级、一级分类、二级分类 | 清单内自定义单选字段，保留源选项和空值 |
| 关联文档 | 有需要时保留为自定义文本字段，并在描述中保留可访问的链接 |
| 已完成 | 原生完成状态；其他具体进度有值时另行保留，不能把「进行中」「阻塞」当成已完成 |

源数据未提供的负责人、日期、分类和历史完成时间不推测。若保留已完成状态时使用了本次完成动作，任务描述说明原表已完成、历史完成时间未记录，避免把导入时间解释为原始完成时间。

## 创建与恢复

1. 用 `task +tasklist-create --as user --name <名称>` 创建清单，立即保存返回的 GUID 和 URL。后续某个字段或任务失败时复用该清单，避免重建整份清单。
2. 创建自定义字段前先看 `task custom_fields --help` 和 `schema task.custom_fields.create`。以 `resource_type: tasklist`、真实清单 GUID 为 `resource_id` 创建字段。单选字段使用 `type: single_select` 和 `single_select_setting.options`；保留返回的字段 GUID、各选项名称与选项 GUID 映射，不把 Base field ID 或选项名称当作 Task option GUID。
3. 逐条用 `task +create` 创建并加入清单。CLI 有专用 flag 时优先使用；其他属性先查 `schema task.tasks.create`，再通过 `--data` 传入。自定义单选值用 `{guid: 字段GUID, single_select_value: 选项GUID}`；文本值用 `text_value`。源字段名称和值不能直接作为 Task API 请求体。
4. 用清单 GUID 和源 record ID 生成稳定的 `--idempotency-key`，保存源记录到任务 GUID 的映射；可在 `extra` 中保存来源坐标。不要把授权信息写入映射或仓库。写入结果不明时先回读，以相同幂等键恢复，避免重复创建。
5. 对源数据已完成的任务，用 `task +complete --task-id <任务GUID>` 保留原生完成状态。有可信历史完成时间且需要精确保留时，先查询当前创建／更新 schema 再使用支持的时间字段。

新清单的成员共享按用户要求处理；不要因为源表有人名就把所有人自动设为清单编辑者。迁移完成后保留源表，删除、归档或持续同步均按用户的单独要求执行。

## 权限与验收

- 按实际操作核实所需 scope：创建清单和任务通常需要 `task:tasklist:write`、`task:task:write`；自定义字段需要相应 `task:custom_field` 写权限；回读任务详情需要 Task 读权限。以当前 schema 和缺失权限响应为准，按 `lark-shared` 补充本次任务所需范围。
- 授权不足时先完成可独立进行的读取和映射；按设备授权流程展示原样链接与二维码，用户确认后完成登录并复用已取得的导入状态。
- `task.tasklists.tasks` 列表可能只返回标题、负责人、日期、完成时间等摘要。核对自定义字段与描述时，用 `task.tasks.get` 读取所需详情；先查对应 schema，再调用原生命令。
- 对照来源核验有效任务数、分页、标题、描述、负责人、按上海时区解释的日期、分类选项值、关联文档和完成状态。全天日期比较日历日期，不强求源与目标毫秒时间戳相同。
- 交付清单返回的 URL，说明导入数、跳过数与已完成数。用户之后可在任务清单中勾选完成，并按未完成／已完成筛选。
